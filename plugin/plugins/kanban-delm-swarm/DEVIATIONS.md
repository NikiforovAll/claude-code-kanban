# Deviations from DeLM

The swarm plugin follows the DeLM product plugin (version 0.3.1): its board (`src/board/mod.rs`), its worker policy (`plugin/worker.md`) and its Claude Code adapter (`hosts/claude/`). Paths in the DeLM column are relative to that plugin. The research harness (`research/board/shared_context.py`, `research/prompts/prompts_n2.py`) is a secondary source: where we follow it and not the product, the row says so.

Rules:

- Follow DeLM's protocol and behavior.
- cck is the visual layer and the host. It shows the swarm and runs the worker sessions. It holds no task policy.
- Reuse a Claude Code feature where one exists.
- Every deviation states its reason. A row with no reason is a gap to close.

DeLM's own runtime does not run here. It refuses any OS but macOS (`src/compatibility.rs:431-434`). Its board imports `std::os::unix` with no platform gate (`src/board/files.rs:7-8`, `src/board/reader.rs:6`). It publishes through APFS clones (`src/workspace/mod.rs:250-286`), and the team is fixed at 2 (`src/board/mod.rs:98`). So we keep our own store in Node (`scripts/store.mjs`, `node:sqlite`) and bring it to the product board's tools, schema and rules. The case names in DeLM's `src/board/tests.rs` are the test list for the store.

## Deviations with a reason

| Area | DeLM | Ours | Reason |
| --- | --- | --- | --- |
| Start | The parent's launch turn makes two native `fork` Agent calls (`hosts/claude/skills/run/SKILL.md:8`, `hosts/claude/hooks/delm.js:714-725`). | The parent writes a spec from its conversation: goal, constraints, decisions, acceptance checks. `start.mjs --spec-file` stores it as request revision 1 and has cck dispatch each worker as a fresh Claude Code session with that spec, the path of the parent's transcript and the worker policy (`scripts/start.mjs`). | A spec carries only what the goal needs, so each worker's context is small and on the point. A worker that needs more reads the parent's transcript. The research harness also starts workers fresh from a task prompt. DeLM uses native forks to work around its host. A plugin's `$.agent.spawn` is refused in Auto mode, so the parent must make the call (`docs/claude-integration.md:9`). It has no host process, so the parent supervises. Its only UI is the terminal's Pane and AbovePrompt surfaces. cck removes all three limits. A dispatched worker also has its own terminal that the user can open and type into, and it outlives the parent. |
| Request record | The request is a record with revisions. Each prompt the user types in the parent is a new revision for both peers (`src/board/mod.rs:121-138`, `delm.js:972-1043`). | The spec is revision 1 of the request, written by `start.mjs` before the dispatch (store command `spec`). Each worker gets it in its dispatch spec, never as an update. The supervisor revises the request with `supervisor.mjs request` when the scope changes (see the direct answer row). Every store response carries the current revision, and a worker that has not acknowledged it gets the change in that response. An idle worker gets it when its mod wakes it (see the waiting and wake row). | DeLM appends the revision to a busy peer's next turn through `session.append`. Carrying it in board responses gives the same next-turn delivery with no host API. |
| Supervisor as a board actor | The parent only forwards the user's text. Only the peers create tasks (`plugin/worker.md:5`). | The parent session acts on the board as the supervisor. Workers see it as actor `supervisor`; in code and in cck's session tree it stays the parent. The first worker makes the first split (see the first split row). The supervisor can create a task when the user changes the scope, assign a new task to a named worker, close an open task with a reason, and release a claimed task. A release bumps the version, so the owner's next update fails as stale and it reads the board again. Workers create, claim, split and release tasks as in DeLM. | The parent has the user's context and does no work of its own. Course corrections can become visible tasks, not text that each worker turns into tasks on its own. "Supervisor" tells a worker what that actor does (checks the result, answers blockers) without implying that it assigns the work, which the peers coordinate. |
| Supervisor surface | No parent tools: the runtime acts for the parent. | No swarm tools in the supervisor. The `/swarm` skill runs `scripts/supervisor.mjs`: `watch` under Claude Code's `Monitor` tool, and one store command per call (`status`, `list`, `expand`, `task_create`, `task_close`, `task_release`, `request`, `end`). | Tool schemas cost context in every turn of every session that loads the plugin. A CLI the skill names costs nothing until a swarm starts. `Monitor` is the Claude Code feature for a stream of notices. |
| Supervisor notices | The runtime marks a `blocked` worker and tells the parent nothing. At a candidate it stops the peers, delivers, then posts the final report to the parent (`src/claude/controller.rs:802-887`, `delm.js:219-235`). When every worker is idle with no candidate, it stops with "No active worker can continue". | `supervisor.mjs watch` prints one line for each `complete` or `blocked` outcome and each stopped worker, and one stall line per board change when no worker runs and none would wake (store command `notices`). It exits at the end. The cursor is in the store, so a watch armed again after `Monitor`'s 30-minute limit repeats nothing; a cursor write does not count as a board change, so it wakes no worker. It reads the `changes` file every 1.5 s and opens the store only when it moved. | The user sits at the supervisor's terminal, and workers have no one to ask. A blocker reaches the supervisor, which answers it with a message or a request, or asks the user first. A stall is a notice, not a stop, so the supervisor can send a request that resumes the workers. |
| First split | Every peer may create and claim tasks; no peer is named to split first (`plugin/worker.md:5`). | We follow the research harness: the first worker in the roster makes the first split and starts its own part in the same turn, and the others explore the entry point and the environment until a ready task is on the board (`STARTUP_A` and `STARTUP_B` in `research/prompts/prompts_n2.py:40-62`, as text in each worker's spec from `scripts/start.mjs`). The supervisor seeds no tasks. | Workers that start from the same spec tend to split the work the same way and race to create the same tasks. A roster order avoids that race without a planner or a planning gate, which DeLM leaves out on purpose (`research/board/shared_context.py:149`). |
| Direct answer | Every text the user sends is a new request revision for both peers (`docs/claude-integration.md:45`). | The supervisor answers one worker with Claude Code's `SendMessage` to the worker's name when the answer leaves the request as it is, and sends a request only when the answer changes the request for every worker. Workers do not message each other (`worker.md`). | A revision wakes every worker, refuses declarations made under the old one and drops a candidate: a cost that fits a scope change, not an answer to one question. The supervisor decides which it is. A misjudged answer leaves the other workers with the old understanding, so when in doubt it sends a request. |
| Claiming a parent task | None. | A new open task wakes an idle worker through its mod (see the waiting and wake row), and that worker claims it. When every worker is busy, the task waits on the queue. A task with `assignee` is created claimed by that worker at version 1. | A task the parent adds must not wait for a worker that is idle. |
| Worker stop notice | Claude tells the parent when a fork stops, and DeLM then releases that worker's claims (`docs/claude-integration.md:49`, `src/claude/controller.rs:823-828`). | The worker's mod calls `worker_stop` when its session ends (an exit, a logout, or the end of a `-p` run; not `/clear` or a resume). | A dispatched session is not a fork, so no native notice comes. The session's own `session.end` hook is the closest notice. A crash is a gap below. |
| Worker policy | `plugin/worker.md`, in each fork's launch context. | `worker.md`, the same text with our tool names, at the end of each worker's spec (`scripts/start.mjs`). Changes: peers instead of two peers; the worker's git worktree instead of a private snapshot; no `task_number` sentence. Evidence is the command, its files and its result in the publication summary, not a receipt. A preview is shared as a finding, not through `delm_service`. The last paragraph names the supervisor, which checks a complete result and answers a blocked outcome by a message or a request, in place of the runtime. A closing paragraph makes the supervisor's messages authoritative and keeps peer coordination on the board. | A dispatched worker is a fresh session, so the policy goes into its spec. The other changes follow the rows for the worker count, workspace, supervisor notices, and the gaps for check receipts and shared services. |
| Outcome checks | `checks` are IDs of native commands the runtime observed, and `shared_checks` are receipt IDs (`src/run/mod.rs:1412-1415`). | `checks` are free text, at most 64 strings of 1024 bytes each: the command and its result. No `shared_checks`. `artifacts` is a path list as in DeLM, `[]` for source-only work. | No runtime observes the worker's commands. Receipts are #36. |
| Candidate | At a `complete` candidate the controller stops the peers and delivers (`src/claude/controller.rs:846-860`). | The first `complete` outcome at the current revision is the candidate. While it stands, the store refuses every worker change except `worker_stop` (a replay still answers), and `wake` wakes no one. A new request revision or the end lifts it. | The peers are separate sessions that no one can stop. The refusal tells a running peer to end its turn. The supervisor checks the result and can send a request if it falls short. |
| Worker count | Fixed at 2 (`src/board/mod.rs:47`, `:98`; `hosts/claude/skills/run/SKILL.md:10`). | `--n` from 2 to 4, default 2 (`scripts/start.mjs`). The store has no fixed count. | The research harness runs 2 or 4, with a prompt tuned for each (`research/delm.py:36`). The product's fixed 2 comes from its two-fork launch, which we do not use. |
| Workspace | A copy-on-write snapshot of the project, with a private Git folder per worker (`src/workspace/prepare.rs:203-205`). | One git worktree per worker, through Claude Code's `--worktree`. | Windows has no APFS clone, and the worktree is a Claude Code feature. |
| Publication storage | Immutable APFS clones outside the worker trees (`src/board/files.rs:141`). | File contents in the store's SQLite file. | Windows has no APFS clone. A stored copy is immutable too. |
| Task id | `task_id` is the event sequence and `task_number` is a display row (`src/board/mod.rs:829-834`). | The store id is the Claude Code task id in the swarm's task list folder. The version is the event sequence, as in DeLM. | cck shows Claude Code task files keyed by id. |
| Publication storage detail | Each file is `{path, base, result, object}`, with the object a clone on disk (`src/board/mod.rs:1247-1270`). | Each version is `{sha256, bytes, executable}`. Contents go to a `blobs` table keyed by hash, so a base that many publications share is stored once. | Windows has no APFS clone. The hash is checked before an apply writes, as DeLM checks the object. |
| Large publications | `large_artifact` raises the limit to 16384 files and 4 GiB. | Only the default limit: 1024 files and 64 MiB. | The contents sit in one SQLite file that every call opens. |
| Executable bit on Windows | Read from the file mode. | On Windows a file takes its executable bit from the version it is compared with: the base for a publish, the published version for an apply. | Windows has no executable bit. The base's bit comes from the commit tree. |
| Task number | A task has a `task_number` display row besides its `task_id` (`src/board/discovery.rs`). | No `task_number`: the task id is already a small display number. | See the task id row. |
| Lost claim | A refused claim returns an error only. | It also logs a `claim_lost` event with the task, its owner and its state, and the error names the task and the owner. | The viewer shows who lost a race for which task. The event changes no task. |
| Read-only export and diff | None. | `store.mjs export` (events after `since`) and `store.mjs diff` (one published file against its base) open the store read-only. They are not worker tools. | The viewer reads the store and must never write to it. `swarm_expand` is read-only too, as in DeLM. |
| Owner filter | `owner: peer` is the other slot. | `owner: peer` is any worker other than the caller. | The worker count is 2 to 4. |
| Wait dependency | `worker:1` or `worker:2`, the peer's slot (`src/board/mod.rs:1116`). | `worker:<name>`, the worker's name from the registry. | The worker count is 2 to 4, and the workers know each other by name. |
| Waiting and wake | `delm_complete(waiting)` ends the turn. The controller checks readiness after each board change and resumes a ready waiter, and `update()` resumes idle workers with the new request (`src/claude/controller.rs:902-926`). DeLM forbids polling loops (`plugin/worker.md:7`). | `swarm_complete(waiting)` with a dependency ends the turn, as in DeLM. `partial` gets DeLM's resume text when the turn ends. A turn that ends with no outcome gets DeLM's repair text once; a second one becomes a `blocked` outcome. Each worker's mod reports its turns to the store (`turn`). The store counts each transaction that changed something in a `changes` file in the swarm folder, and answers the count to `turn` and `wake`. While the session is idle, the mod reads that file every 1.5 s. When another worker's change moved the count, the store's `wake` decides, and the mod submits DeLM's resume text as a prompt. A worker wakes for a request revision it has not seen, a pending partial or repair resume, a ready dependency, the no-producer rule, or, when it is idle but not waiting, any new available task or publication. No wake while a candidate stands, after the end, or for a stopped worker. Each wake logs `worker_woken`. | No host process runs here, and a parent wake would cost a parent turn and stop when the parent is busy or closed. Every worker already runs the mod, which can submit a prompt to its own idle session. A read of a small file per 1.5 s costs far less than a store call per poll. The database files change on reads too (the WAL file comes and goes), so the count is the signal. |
| No producer | When every worker has no turn and no resume is pending, each waiter not yet repaired is resumed once (`src/claude/controller.rs:866-886`). | When no worker has a running turn, a waiter wakes with DeLM's no-producer text, once per request revision (`wait_repaired`). | The same rule. The store knows each worker's turn from the mod's reports, so the first idle worker that sees the change resolves it. |
| Aborted turn | A turn that ends without a completion is blocked, and its claims are released. | An interrupted turn (`reason: 'aborted'`) changes nothing in the store and gets no repair wake. The worker stays as it was, and its claims stay. A failed turn (refusal or error) counts as a turn with no outcome. | The user can interrupt a dispatched worker in its terminal to steer it. A release there would hand its task to a peer. |
| Readiness in the board | Not shown (`src/run/mod.rs:1270-1345`). | The board shows `running` for each worker, and `ready` and `stalled` for each waiting worker, from the same rules `wake` uses. `export` carries each worker's `running`. | The viewer and the supervisor see why a worker sleeps or wakes. |
| Revision ack | A worker acknowledges a revision when it declares completion (`src/board/mod.rs:1051`). | Any change a worker makes acknowledges the current revision, because that response already carried the change. Completion still checks `expected_revision`. | A response gives each unacknowledged change once. Without the ack, every later response would repeat it. |
| Replayed response | A request row keeps the whole response, board included, and a retry returns it as it was (`src/board/mod.rs`). | A request row keeps the result only. Every response, a retry too, carries a board read after the commit. | Each mutation would store a board of up to about 100 KB that is never pruned, and building it would hold the write lock longer. A retry also gets the current board, which is what the worker needs next. |
| Worker names | Slots 1 and 2, bound to the native agent id (`delm.js:719-733`). | `w<i>-<hex>`, the session's cck name and peer name. Identity still comes from the host (`$.session.id()`). | cck shows the names, and `SendMessage` uses them. |
| Board | Native `Pane` or `AbovePrompt` in Claude Code's terminal (`hosts/claude/hooks/board-view.js`). | The cck board and a cck group per swarm. | cck is the visual layer. |
| Tool transport | An MCP sidecar behind a Unix socket, with a one-use ticket per call (`delm.js:839-865`, `src/claude/mod.rs:289-340`). | `$.tool.register` in a mod, and one `node store.mjs` process per call (`hooks/swarm.ts`). | It reuses Claude Code's mod tool API, and Windows has no Unix socket. |
| Claude Code task tools | Not touched. | `TaskCreate` and `TaskUpdate` are refused while a swarm runs (`hooks/swarm.ts`). | The store writes the task files that cck shows. A direct write would split the board from the log. |
| Status and stop | `/delm-status` and `/delm-stop`, registered in every session with `immediate: true`, answer with no model turn. Status opens the board pane. Stop stops the peers with `TaskStop`, confirms they ended (`agent.list`, up to 2 s), and saves unfinished changes before cleanup (`delm.js:620-685`, `board-view.js:572`). | `/swarm-status` and `/swarm-stop`, registered the same way in every session that is not a worker, run `supervisor.mjs board` and `stop` for this session's newest running swarm, or the swarm id given. Status prints the board as text. Stop ends each worker's cck terminal (`dispatch end`), waits up to 10 s until `dispatch list` no longer shows it, marks each worker stopped (its claims go back to available), saves every worker's changes to the recovery bundle, removes the worktrees, then ends the store as `stopped` (see the delivery row). A worker that still runs leaves the swarm running. | The workers are cck sessions, not native tasks, so `TaskStop` cannot reach them. The board pane is the viewer (`/swarm-viewer`). |
| Delivery | The host process delivers a `complete` candidate when the controller stops the peers: a 3-way `git merge-file` of each file into the user's project, all or nothing. The Git index stays as it was, a journal is written first, and the worker trees are removed (`src/workspace/delivery.rs`). Guarded renames refuse a file the user changed during the apply. A conflict on any file writes nothing: every worker's changes go to `workspace/recovery` (SHA-256 named blobs and `complete.json`), the trees are removed and the run ends as `delivery_conflict` (`delivery.rs:569-591`, `:882`). A stop or cancel saves the same bundle (`:1011-1028`). | The same plan, journal, bundle and messages (`scripts/deliver.mjs`), run by `supervisor.mjs end` (`finish`): `complete` delivers the candidate's worktree, `partial` and `stopped` save the bundle. The bundle and the journal are under the swarm folder (`recovery/`, `delivery/`). After the apply, every touched path is read again, and a path that is not at its planned content fails the end with the path named; a rerun resumes from the journal. On Windows the base is read with `git cat-file --filters`, so `core.autocrlf` does not show every file as changed. Ignored outputs count only when the candidate lists them in `artifacts`. The other workers' changes are discarded on a delivered end, as in DeLM. | No host process runs here, so the supervisor's `end` command delivers. Node has no rename that fails when the target changed, so the check after the apply takes the place of the guarded renames: a user edit is never overwritten, but one made in the gap between the check and the rename can be. An undeclared ignored output is lost when the worktree is removed. |
| Open tasks at the end | The run ends with the board as it is; an open task stays open. | `end` as `complete` refuses while a task is open and names each one, before it stops any worker. The supervisor closes a moot task with `task_close` and a reason (after `task_release` for a claimed one), or sends a request for the work it names. After the workers stop, `end` closes every task still open with the reason `the swarm ended as <outcome>`. | The board mirrors the store's tasks into the Claude Code task list, so an open task would show as pending on the board after the end, with no one left to claim it. Two workers can create the same task at once, and only the supervisor can close one. The check before a complete end is a review step, like the check of the candidate's result. |

## Gaps to close

These rows have no reason yet. Most come from one cause: the store was ported from the research harness, not from the product board.

| Area | DeLM | Ours | Task |
| --- | --- | --- | --- |

It also keeps its turn marked running, so the no-producer rule never fires for its peers. A worker that never started counts as running for the same reason. | Not planned yet. |
| Shared services | `delm_service` lists and claims a named preview, and `acquire_check`/`release_check` guard a shared browser or database (`plugin/worker.md:13`). | None. A worker launches its preview with port 0 and shares the URL as a finding. | Not planned yet. |
